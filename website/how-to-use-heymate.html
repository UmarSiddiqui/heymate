How to use HeyMate as a developer, designer, or learner.

HeyMate is a free, open-source AI buddy that lives in your Mac's notch. Hold ⌃ ⌥, ask about anything on your screen, and it answers out loud while its cursor points at what it means. It can also hand real work to Claude Code, Codex, or OpenCode, on the subscription you already pay for.

That is the whole pitch. This guide is about what to do with it on a normal working day, whether you write code, push pixels, or are trying to learn something you know nothing about yet.

The one habit that matters

Stop copying things into a chat box. Keep working, hold the hotkey, and ask the question out loud while the thing is on your screen. HeyMate takes one screenshot when your question needs it, sends it with your words to the model you chose, and deletes it after the answer. Text-only questions skip the screenshot entirely.

Everything below is a variation on that habit. Ask first, and only then decide whether the answer should turn into work.

Set up in five minutes

  1. Install: curl -fsSL https://getheymate.vercel.app/install.sh | bash
  2. Sign in to one CLI you already use: claude auth login --claudeai, codex login, or opencode auth login.
  3. Pick that brain with the model chip in the notch and grant Microphone, Accessibility, and Screen Recording. Here is why each one is needed.
  4. Hold ⌃ ⌥ and say hey.

For developers

1. Ask about the thing you are staring at

A stack trace in the terminal, a failing CI page, an unfamiliar function in a PR. Hold the hotkey and ask:

  • "What is this error actually telling me?"
  • "Why is this test flaky, based on what is on screen?"
  • "Walk me through what this function does, top to bottom."

You get a spoken answer and a cursor pointing at the exact line, so you never lose your place in the editor. There is also a built-in code explainer skill for longer walkthroughs.

2. Hand off work behind an approval gate

Say "HeyMate agent, add dark mode to this project" or "fix the failing auth test". HeyMate does not just start. The flow is always the same:

  1. The selected CLI reads the task and the workspace with writes disabled and drafts a plan.
  2. HeyMate shows you the plan and waits.
  3. You approve. HeyMate takes an undo snapshot, resumes the same CLI session, and lets it write.

Approved work runs in a helper process, so it keeps going if you quit the app. When it finishes you get a completion receipt, and if you do not like the result, undo restores the snapshot. For work you want to watch, take over in Terminal.

Practical rules that make this work well:

  • Give one outcome per job. "Add a retry to the upload client and a test for it" beats "improve the upload code".
  • Read the plan. The plan is the cheap place to catch a wrong assumption.
  • Use Claude Code or Codex when the job must build or run tests. OpenCode jobs can edit files but cannot run shell commands.
  • Point jobs at an existing project folder when the work belongs in your repo. Otherwise HeyMate makes a sandbox folder under ~/Projects/heymate.

3. Give each part of your project its own mate

A mate is a lasting helper with a name, a job, a personality, its own memory, and a workspace folder. You can create one by saying "make me a mate that reviews my Swift diffs", or from the Mates window where you can also set its brain and folder. Mates are good when a role repeats:

  • Release captain. Checks whether the last CI release finished, whether the download asset exists, and reminds you of the manual step you always forget.
  • Reviewer. Pointed at your repo, it reads before it proposes, and its memory remembers the conventions you keep correcting.
  • Docs writer. Drafts changelog notes and README changes, and never publishes them.

Because each mate keeps its own chat, memory, and folder, a question to the reviewer does not pollute your release notes.

4. Put the boring checks on a routine

A routine runs a mate's task daily at a time you choose, or every N hours, and the result lands in that mate's chat. Good first routines are read-only: "every morning, summarize new issues and failing builds" or "every 6 hours, check the release workflow and tell me only if it is red". Missed runs collapse into one, so you never come back to a backlog, and a routine pauses itself after repeated failures.

5. Let Standing Orders propose, never start

Standing Orders are rules you give HeyMate such as "when a build fails on screen, offer to investigate". HeyMate proposes work when a rule matches, but it never starts anything unasked. You stay the approver.

6. Plug in the tools you already use

Connectors cover Apple Calendar, Reminders, Notes, Mail, Messages, and Shortcuts, plus local CLIs such as gh, git, docker, kubectl, vercel, supabase, and stripe using your own logins, any MCP server, and 1,400+ toolkits through Composio. Reads run quietly. Anything that sends, deletes, or pays asks first.

For designers

1. Get a critique without leaving the canvas

Open your Figma frame or a live page and ask "what would you change about the hierarchy here?" or "is this contrast readable?". The built-in UI design critique skill gives structured feedback, and the cursor points at the exact element it is talking about, which is faster than reading a paragraph of description.

2. Learn the tool while you use it

"Where do I set up auto layout on this frame?" "How do I make this a variant?" Because HeyMate sees the real screen and asks macOS for the real button position, it points at the control instead of describing where it probably is. The screen walkthrough skill steps through unfamiliar apps one click at a time.

3. Bridge to engineering

When a design needs to exist in code, describe the outcome and let an agent plan it: "build this card component to match the design on screen, using the tokens in this project". Read the plan, approve, and check the result in your browser. Keep a design QA mate pointed at the front-end folder with one instruction in its soul: flag anything that uses a color, size, or font outside the token file.

4. Keep the boring writing off your plate

Microcopy, alt text, release notes for a design system. Dictation puts your spoken words into the field you are typing in, and a writer mate can polish them with your voice guidelines in its memory.

For learning something new

1. Point at what confuses you

Reading a tutorial, a paper, a spreadsheet, or a settings screen you do not understand? Hold the hotkey and ask "explain this like I have never seen it before", then "what should I learn first?". It answers about the page in front of you, not a generic version of the topic.

2. Make a tutor mate

Create a mate whose job is teaching one subject: "ask what I already know, explain with one small example at a time, quiz me, and keep notes". Its memory and folder persist, so next week it remembers what you got wrong. A built-in study tutor skill covers the same pattern if you do not want a dedicated mate.

3. Learn by doing, with a safety net

Want to understand a new framework? Ask an agent to build a tiny example in a sandbox folder, read the plan so you learn what it intends, approve, then open the result and ask about each file. Nothing touches your real projects, and you can undo.

4. Put a review on a schedule

A daily routine like "at 8am, give me three questions on what I studied yesterday" turns one-off reading into something that sticks.

What HeyMate will not do

  • It will not write, send, click, or delete anything without your approval.
  • It will not run in the background watching you. It takes a screenshot only when you press the hotkey and the question needs it, and never stores it.
  • It will not bill you. There is no HeyMate account. It uses your own Claude, Codex, or OpenCode sign-in, and strips API-key variables from those processes so a stray key cannot switch you to metered billing.
  • It is not a sandbox. Coding CLIs run as your macOS user, and plan mode limits writes, not reads. Read the permissions page and the privacy notes.

Start small

Install it, ask one question about whatever is on your screen right now, and see whether the answer saved you a context switch. Then create one mate for the job you repeat most. That is enough to know if it fits.
