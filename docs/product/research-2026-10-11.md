# HeyMate product, harness, and distribution research

Research date: 11 October 2026, Australia/Perth. This document records the pre-change baseline. Repository metrics are point-in-time observations, not forecasts. Product recommendations below are judgments, not proven explanations of user behavior. Native-app interaction testing belongs in the separate product audit.

## Recommendation

Build **a memorable companion that helps people learn desktop apps and websites, then carry work forward**. macOS is the current host platform, not the limit of the tasks it can teach. Guidance depends on visible screen context and model capability; this is not a promise of compatibility with every piece of software. Keep open source, native performance, user-owned memory, and provider choice as advantages. “Open-source ReferenceRenderer” helps explain the category but gives another product ownership of the story.

Lead with one demonstrable result: “I removed a logo background myself, with a mate pointing out each step.” Then make that same mate remember the lesson and help the person repeat it without starting over. This combines teaching, identity, and continuity. It is more concrete than a notch app, coding-agent dashboard, character-chat app, and automation platform presented with equal weight.

Teaching itself is not unique. ReferenceRenderer and older Mate forks already teach. HeyMate must prove better continuity, control, and outcomes with actual task recordings. Neither repository breadth nor this research establishes that HeyMate is better overall than either competitor.

## Baseline: reach is small; rejection is unproven

Public GitHub observations for [UmarSiddiqui/heymate](https://github.com/UmarSiddiqui/heymate): repository created 28 August 2026, with 1 star and 0 forks at inspection. Release asset downloads count requests, not unique users; they include updates and developer testing. Contributor counts alone do not establish an outside contributor community.

Owner-only GitHub traffic and website analytics were reviewed separately. Detailed figures remain in the local product audit, outside this public repository. The measured audience is small, so it is too early to infer broad market rejection or reliable conversion rates. Recheck comparable time windows after a focused distribution campaign.

GitHub reported no recognized license even though `heymate/LICENSE` contains MIT. Local `.github/ISSUE_TEMPLATE` already has bug, feature, and installation templates; the API's missing template result must not be presented as proof that templates do not exist. Root-level license/contribution work is underway separately.

Only open PR at initial inspection: [#14, HeadlessCLIProcess EOF handler fix](https://github.com/UmarSiddiqui/heymate/pull/14). Avoid duplicating it.

Likely friction, requiring measurement: unsigned installation, unclear primary use case, first-run permission/auth setup, inconsistent mate identity, confusing chat routing, and absent contributor entry points. Low exposure is measured; each conversion or retention explanation remains a hypothesis.

## Competition: relevant lessons

**ReferenceRenderer.** Its official changelog describes personalized Mates with names, faces, memory, jobs, routines, and conversational creation. Recent work emphasizes preserving walkthrough progress, matching follow-ups to the intended character, resilient computer use, and coherent notification behavior. These are good acceptance-test topics. The lesson is product continuity and recovery, not maximum feature count. Changelog is vendor-reported behavior, not an independent benchmark. [Official changelog](https://www.reference-renderer.com/changelog), checked 11 October 2026; latest listed release 1.0.53 dated 2 October.

**OpenMate.** There are multiple repositories with this name. The main comparison here is Jason Kneen's native Swift project, MIT licensed, with 553 stars when queried through GitHub. It credits Farza's upstream and teaching forks. It offers screen guidance, tools, agents, and direct updates. Its feature list is substantial; “heaps better” needs task evidence. A different `proyecto26/openmate` is a Claude Code skill/plugin plus native companion path, not the same product. [Jason Kneen repository](https://github.com/jasonkneen/openmate), [separate plugin project](https://github.com/proyecto26/openmate).

**Traycer.** Useful reference for shared task context, provider switching, agent-to-agent handoffs, and durable artifacts. Important boundary: its MIT public repository contains clients, CLI, and protocol; its Host and cloud backends are not included. It is not a complete open-source harness ready to embed. Retain HeyMate's SwiftUI experience and borrow explicit task/session contracts. [Product](https://traycer.ai/), [repository architecture statement](https://github.com/traycerai/traycer/blob/main/AGENTS.md).

**Dots / Grok / Muse.** These names describe different experiences. Current ChatGPT Dots emphasize ongoing responsibility, identity, memory, and inspectable task activity. Grok's official FAQ describes Companions as an iOS feature. Meta Muse emphasizes persistent personal work and user-controlled connected apps. Their useful shared pattern is a recognizable agent whose context survives, not proof that adding avatars alone produces adoption. No comparable retention evidence was established. [Dots setup](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot), [Grok FAQ](https://docs.x.ai/grok/faq), [Meta Muse announcement, 8 September 2026](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/).

## Meta harness: state first, framework second

HeyMate already has `HeadlessCLIAdapter`, `AgentRunStore`, detached execution, `MateProfile`, `MateWorkspace`, and `MemoryRepository`. Replacing these wholesale is not prerequisite to fixing personas. The current `MateSoul.promptBlock` returns no identity block when personality text is empty; persona wiring must be audited across talk, agent execution, follow-ups, routines, restart, and provider changes.

Proposed native contract:

1. **Stable mate context.** Every request carries `mateID`, identity revision, conversation ID, memory scope, workspace, provider session ID, and permission scope. All visible messages and spoken replies use that same mate identity. “HeyMate” remains product identity and first mate only where intended.
2. **One run state model.** Distinguish planning, awaiting approval, running, awaiting user, rate limited, interrupted, failed, and completed. Persist transitions and provider session IDs. A process exit code alone cannot prove task completion.
3. **Explicit provider capabilities.** Negotiate resume, images, tools, approvals, cancellation, and usage reporting. Disable unsupported actions rather than presenting false equivalence between engines.
4. **Bounded context.** Stable shared instructions, mate identity, relevant memories, current task state, and recent evidence each have a clear role. Do not resend entire chat histories or every screenshot on each turn.
5. **Inspectable memory.** Separate mate knowledge, user-approved shared preferences, task evidence, and disposable summaries. Record provenance/time, offer edit/delete, and never silently leak one mate's private task into another.
6. **Teaching state.** Store goal, current step, expected observation, completed steps, recent failed attempts, and user corrections. Wait for evidence of a step before advancing. Offer “hint,” “show me,” “I did it,” and “pause”; end with a short reusable recap.
7. **Measured delegation.** Default small tasks to one agent. Spawn specialist/reviewer roles when independent work or verification warrants their latency and quota cost. Add checkpoints and a stop/budget control before an autonomous multi-agent loop.

Migration order: fix identity/context contracts in existing adapters; add deterministic regression coverage; prototype Codex app-server behind the same boundary; evaluate ACP and Letta against measured gaps. Do not expose new framework names to normal users.

Acceptance cases: two mates with conflicting styles and separate facts; empty personality; rename; switch mate while response streams; routine resumes after sleep; provider sign-out; cancellation; request interrupted by follow-up; retry after failure; lesson step repeated after wrong click; provider switch without falsely claiming access to unavailable memory. UI, text, voice, and stored results must agree on ownership.

## Subscription integration: preserve official routes

**Claude Code.** Current official terms explicitly permit running the unmodified binary in products when conditions are met, with each end user authenticating through their own subscription, API key, or supported provider. They separately prohibit custom Claude.ai login/proxying of user subscription credentials. HeyMate's `SubscriptionSignIn.swift` invokes official installers and CLI browser sign-in; that is materially different from extracting tokens for a custom HTTP client. Audit the full integration and terms before distribution. Preserve user authentication choices; stripping API credentials should correspond to an explicitly selected subscription mode, not removing supported methods entirely. [Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), sections “Can customers offer Claude Code in their products?” and “Authentication and credential use.”

**Codex.** Official app-server documentation provides structured threads, turns, events, approvals, and account state. It explicitly permits existing local/open-source app-server authentication while recommending migration to Sign in with ChatGPT; it distinguishes commercial/hosted services. This makes app-server a strong fit for HeyMate's local open-source architecture. Use documented authentication and scoped ownership, not copied browser tokens. [App-server documentation](https://learn.chatgpt.com/docs/app-server), [Sign in with ChatGPT app-server integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server).

Neither subscription implies unlimited work or unrestricted model access. Show provider identity, limit/reset states where available, and interruption recovery. Avoid “no second bill, ever” promises across optional paid connectors, voices, APIs, and future provider terms.

## REA: useful research tool, not the first product fix

[morluto/rea](https://github.com/morluto/rea) is MIT licensed. Its documentation describes local package/resource inspection, native analysis via Hopper/Ghidra/IDA, JavaScript analysis, and runtime evidence capture. Setup changes agent configuration; native analysis needs an engine. No installation or analysis of ReferenceRenderer's binary was performed by this research task.

Use it only for a concrete unanswered implementation question after observing public behavior and checking available MIT source. Example: understanding how a native panel follows display changes, followed by an independently written HeyMate implementation and test. Keep evidence and limitations. The tool's MIT license does not grant rights to copy a target app's code, assets, private services, or credentials. Avoid authentication/payment bypass and treat modern ReferenceRenderer separately from its older open-source Mate ancestor.

## Instrumentation that answers product questions

Keep two jobs distinct: Sentry for reliability, existing PostHog for product outcomes. Sentry supports macOS error reporting and advertises a free Developer tier; verify actual account quotas in its dashboard before configuration. [macOS SDK](https://docs.sentry.io/platforms/apple/guides/macos/), [pricing](https://sentry.io/pricing/).

HeyMate already has typed events and bounded error metadata in `HeyMateAnalytics.swift`. Current setup activates when a build provides a PostHog key. The function alone does not establish user opt-in; check the full consent path before enabling. A code comment saying opt-in is insufficient.

Add minimal events: setup stage completed/failed, first successful answer, mate created, first mate reply, lesson started/step verified/completed, run completed/blocked/failed, resume success, and voluntary usefulness rating. Include version, engine, duration, bounded error category, and feature enum only. Exclude prompt text, responses, screenshots, microphone audio, file paths, URLs, account addresses, and connector tokens. Keep diagnostics inspectable, redact before upload, and offer separate consent.

Measure weekly: time to first useful answer, first-day lesson completion, second-session return, successful mate reuse, crash-free sessions, and where authentication or permission setup fails. Stars remain a distribution signal, not the primary success metric. Avoid native desktop session recording; Hotjar's website journey tools belong on the landing page only if a specific web-conversion question remains. [Hotjar web journey examples](https://help.hotjar.com/hc/en-us/articles/115011819928-Recording-Filters).

## Distribution gates and campaign

**Before broad promotion:** stable mate identity in every entry point; coherent chat ownership; first useful lesson without developer assistance; predictable cancel/retry/resume; truthful permission/privacy/cost copy; clean installation and update path. Obtain Developer ID signing/notarization for mainstream Mac distribution rather than making security-bypass instructions the default first impression.

**Landing page:** replace ambiguous “It's already looking” with a specific teaching outcome and on-demand capture wording. Show an uncut task clip near the first download button, one real finished result, supported engines/requirements, and straightforward installation. Keep mates, automation, and notch utilities as supporting depth. The local page already contains demonstrations, social metadata, and rich feature sections; the problem is message hierarchy and credibility, not absence of content. Live visual verification belongs to the browser audit.

**Contributor path:** recognized root license, concise build guide, architecture map, contribution guide, useful issue templates, five genuinely scoped starter issues, and a current roadmap with owners/status. Invite contributions to observable pain: mate identity, teaching checks, accessibility, reproducible provider errors, and desktop-app and website teaching recipes. Count first successful external builds and merged outside contributions.

**First campaign:** publish a truthful 30–45 second Photopea lesson, a 15-second mate-memory follow-up, and a concise before/after changelog. Show real waits/errors or label cuts; do not fabricate testimonials, usage counts, benchmarks, or endorsements. Caption-first formats for X/Instagram and a longer walkthrough for YouTube. One demo, one use case, one CTA.

Recruit a small cohort of creators and learners who use macOS. Cover tasks in desktop apps and websites, observe completion, fix the common blockers, then expand. Give each interested creator a repeatable task, setup requirements, screen footage, and honest comparison notes. Do not claim superiority or contact influencers en masse on unmeasured product assumptions. Ask users for a star after a demonstrated win, and for a bug report when setup fails.

Suggested release exit criteria are targets, not current results: ten observed first-run sessions; at least eight complete the flagship task without developer rescue; zero identity crossover in the acceptance suite; tested upgrade and rollback path; published known limitations; measured second-session reuse. Marketing can begin with a clearly labeled preview before those gates, but broad-launch claims should wait for evidence.
